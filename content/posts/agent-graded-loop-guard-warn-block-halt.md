在自主 Agent 执行中长周期任务（如代码重构、排查复杂 Bug 或分析日志）时，最令人头疼的异常现象之一就是**局部死循环**（Looping Behavior）。

最常见的场景莫过于：模型使用某个未匹配到的正则表达式连续发起了 3~4 次完全相同的 `grep_search`，或者不断用相同的路径参数调用 `read_file`。每一次调用都返回完全相同的空结果或错误，但模型依然固执地在原地打转。

传统 Agent 框架面对死循环的处理手段通常非常粗糙：
1. **放任自流直至耗尽 Max Turns**：白白浪费数十轮 API 调用和海量 Token，最终以“超过最大迭代轮数”惨烈崩溃；
2. **暴力抛出 Exception 强行中断**：一旦检测到重复调用，立刻抛出异常终止任务。这导致前面所有已经收集到的上下文、分析事实和推理成果瞬间作废，用户只能重头再来。

为了兼顾**任务成功率**与**预算安全性**，我们在 Agent 运行时中引入了**分级循环守卫（Graded Loop Guard）**，建立起一套从「温和警告」到「合成拦截」再到「终态熔断」的阶梯式治理体系。

## 1. 为什么“一刀切”的熔断行不通？

在工程实践中，判断模型是否在“打转”远比想象中微妙：

- **只读探测 vs 状态变更**：对于只读幂等工具（如 `grep`、`view_file`），模型在不同子步骤中查阅同一个配置文件并不一定是有害的死循环；但如果是执行带副作用的变更工具（如 `write_to_file` 或 `run_command`），连续执行完全相同的写入或构建命令则极具风险。
- **参数虽然相同，但时序上下文已变**：例如在执行了某个命令后再次调用 `git status`，虽然入参完全一致，但外部系统的状态已经发生了变化。
- **大模型具备自我纠偏潜力**：许多时候，模型并不是无法解决问题，而是在当前推理分支中钻了牛角尖。如果能在结果中给它一句恰到好处的提示（“*你已经用相同参数查询了 2 次且无结果，请检查路径或更换检索关键词*”），模型往往能够立刻跳出思维定势，换一种方案继续完成任务。

因此，循环守卫的核心哲学应当是：**先引导纠偏，再物理拦截，最后兜底熔断。**

## 2. 状态机与分级处置阶梯设计

我们在 Agent 主循环的 `before_tool_call` 拦截阶段接入了纯逻辑、无副作用的判定状态机：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum LoopGuardAction {
    /// 放行：首次或正常调用
    Allow,
    /// 警告：注入引导文本到 tool result，工具照常执行
    Warn,
    /// 拦截：阻止物理执行，合成错误结果返回
    Block,
    /// 终止：结束本轮交互
    Halt,
}
```

### 第一阶：Warn（引导注入）

当检测到相同工具、相同规范化入参（`canonical_args_hash`）在同一次任务中出现第 2 次时：
- 守卫放行底层工具的物理执行；
- 工具返回结果后，系统在 `ToolResult` 的末尾自动追加一段引导型系统提示：
  > `[系统提示] 检测到你已经连续以相同参数调用了该工具，且未取得新进展。请不要重复执行相同调用，尝试更换搜索关键词、调整路径或改用其他工具。`
- 绝大多数主流推理模型在读到该提示后，都能在下一轮主动调整策略（例如从 `grep` 改用 `find_by_name`，或修改正则语法）。

### 第二阶：Block（合成拦截）

如果模型忽略了警告，发起第 3 次完全相同的调用：
- 守卫直接**短路（Short-circuit）**物理工具执行，不再产生真实的文件 IO 或子进程启动开销；
- 系统在协议层合成一个结构化的错误返回（`ToolResultContent::Error`），明确告知模型底层已拒绝重复执行；
- **严格维持协议完整性**：在底层传输协议中，大模型的每一个 `tool_use` 必须有对应的 `tool_result` 严格闭合，合成错误能够保证对话上下文协议不被破坏。

### 第三阶：Halt（安全熔断）

当重复调用达到第 4 次（`HALT_AFTER = 4`）时，说明模型已彻底失去逻辑自愈能力：
- 运行时立刻安全终止本 Turn，触发 `RepeatedToolCalls` 终态事件；
- 前端与审计日志明确收到 `repeated_tool_calls` 的具体工具名称与入参详情，替换掉以往令人困惑的“达到工具迭代次数上限”模糊文案；
- 会话的完整上下文与此前所有成功的历史证据全部被完整持久化保留，用户可以直接在当前进度上补充提示词继续推进，无需从头重跑。

## 3. 工具类型与结果签名的精准判定

为了防止误伤正常的多步骤操作，守卫引入了双重校验维度：

1. **参数规范化哈希（Canonical Args Hash）**：
   JSON 字符串中的键值顺序可能是随机的（如 `{"a": 1, "b": 2}` 与 `{"b": 2, "a": 1}`）。守卫首先对参数 JSON Value 进行递归的 Canonical 排序与序列化，再计算哈希值，确保参数等价性判断 100% 准确。
2. **区分工具副作用分类**：
   只读工具（`ReadOnly`）与变更工具（`Mutating`）配置不同的容忍度阈值。只读工具允许更宽容的探索，变更工具则执行更严格的拦截控制。

## 4. 收益与工程启示

引入分级循环守卫后，我们在复杂长任务实测中取得了显著成效：

- **自愈率大幅提升**：在产生重复调用的边缘 case 中，超过 **70%** 的任务在 `Warn` 阶段即被模型自行纠偏成功，避免了任务失败；
- **杜绝无效 Token 浪费**：在 `Block` 与 `Halt` 阶段拦截了无意义的重复巨型工具输出，杜绝了上下文爆炸；
- **透明精准的终态归因**：当任务确实无法继续时，用户能清晰知道是哪个工具在什么参数下陷入了死循环。

优秀的 Agent 治理机制绝不是在出错时粗暴地拉下电闸，而是像成熟的交通信号系统一样，通过由浅入深的信号梯队，引导模型在正确的轨道上平稳运行。
