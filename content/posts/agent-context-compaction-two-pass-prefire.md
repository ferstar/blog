在构建长周期、自主执行复杂任务的 Agent 时，上下文窗口（Context Window）始终是悬在头顶的达摩克利斯之剑。

当一个会话跨越数十轮交互、调用了上百次工具（读取文件、搜索代码、执行测试、分析日志）后，上下文 token 必然逼近上限。过去的常规做法通常是触发一次同步压缩（Single-pass Compaction）：把历史消息打包发给 LLM 做一段综合摘要，替换掉旧消息。

但这套简单粗暴的做法在实际业务中会遇到几个让人非常难受的问题：

1. **前台明显卡顿**：压缩触发时，Agent 主循环必须暂停，发起一次针对海量上下文的 LLM 摘要请求。用户端看到的现象就是输入框被阻塞，或者 Agent 突然“假死”数秒到十几秒。
2. **细节不可逆丢失**：一旦被概括成几行自然语言，前面排查过的具体堆栈行号、零散配置参数或测试细节就灰飞烟灭了。如果后续步骤需要这些细节，模型只能重新调用工具查一遍，甚至陷入幻觉。
3. **KV Cache 被击穿**：如果直接把生成的 summary 塞进 System Prompt，会导致大模型服务端的 Prompt Prefix 发生变化，破坏整个前缀缓存（Prompt Caching），后续每一次交互的首字延迟（TTFT）与计费成本都会激增。
4. **无效摘要浪费**：很多时候上下文爆炸只是因为某几个工具返回了巨型输出（如超长的 `git diff` 或 `cargo check` 日志），只要修剪掉这些工具输出即可腾出大量空间，却依然走了一遍昂贵的 LLM 全文摘要。

最近三天，我们针对智能体运行时（Agent Runtime Harness）的上下文管理机制做了一次深度重构。核心目标很明确：**把耗时压缩剥离出主流程，让历史细节可回捞，让状态机在临界点具备确定性。**

## 1. Two-Pass Prefire：把耗时压缩移出主路径

消除用户感知卡顿最有效的方式，是在真正超限之前，把最重的工作在后台异步做完。我们借鉴了工业级 Agent 的设计思想，实现了 **Two-Pass Prefire** 两阶段压缩机制。

### 阶段一：前缀预热（Pass 1）

我们在配置中引入了提前量（`prefire_margin_tokens`，例如预留 10% 缓冲空间）。

当上下文占用达到阈值的 90% 时，Agent 不会打断当前交互，而是在后台异步派发一个 Pass 1 任务：
- **前缀切分**：提取前 95%（`prefire_prefix_fraction`）的历史消息。切分时严格保护 `tool_use` 与 `tool_result` 的配对关系，绝不切断尚未闭合的工具调用。
- **中间载体提取**：将前缀历史送入后台 LLM，提炼出结构化的前缀笔记（`NOTE1`），并对输入前缀计算轻量指纹（Fingerprint）。
- **非阻塞缓存**：整个 Pass 1 完全在独立的异步 Tokio 任务中执行，前台用户与 Agent 依然正常流式交互。

### 阶段二：增量压缩（Pass 2）

当后续交互让总 token 正式突破 100% 压缩阈值时，主循环进入正式压缩：
- 校验 Pass 1 的前缀指纹。若前缀未被意外篡改且后台任务已完成，直接提取缓存的 `NOTE1`。
- LLM 不再需要阅读几十 KB 的原始历史，只需要将紧凑的 `NOTE1` 与 Pass 1 之后产生的新增尾部消息（Tail Messages）合并，生成最终的压缩摘要。
- **优雅降级**：如果前缀发生漂移或 Pass 1 意外失败，系统会自动回退到传统的 Single-pass 单次压缩，保证功能正确性。

通过这种方式，正式触发压缩时 LLM 处理的输入量缩减了 80% 以上，主流程的等待时间降至毫秒级。

## 2. 可回捞设计（Recovery Hint）：压缩不是删除

很多 Agent 框架在压缩后，会将旧消息从内存和持久化中彻底丢弃。这会导致 Agent 在长任务后半段变成“健忘症患者”。

在我们的设计中：
1. **Append-Only 唯一事实来源**：所有的原始消息、工具调用及其完整输入输出，自始至终完整追加写入底层的 Session JSONL 文件中，永不物理删除。
2. **可回捞指针注入**：在生成的 `<compaction-summary>` 结构后，系统会自动附带 `<recovery_hint>` 标签，明确告知模型：
   - 当前历史已经过概括；
   - 原始完整对话保存在本地 JSONL 路径中；
   - 若后续需要确认具体的文件路径、报错行号或中间产物细节，可以直接使用只读工具（如 `view_file` 或 `grep_search`）回读该文件。
3. **保持 System Prompt 冻结**：摘要信息统一作为独立的对话消息注入，绝不污染 System Prompt。这保证了模型供应商服务端的 Prefix Caching 稳定命中，大幅降低了 API 计费与首字延迟。

## 3. Prune-Only 优先与终态检查点

除了两阶段压缩与回捞机制，我们还在边界控制上补齐了两个关键闭环：

### 纯修剪优先（Prune-Only Retry）

压缩的第一步其实是修剪（`trim_old_tool_results`）。很多时候，用户执行了一次 `find` 或查看了一个巨大文件，只要把几轮之前的超长工具返回截断为预览摘要，上下文即可瞬间释放数万 token。

过去如果修剪后没有触发语义摘要，状态机容易误判为“上下文未发生改变”而直接抛出溢出错误。现在我们显式跟踪 `tool_results_trimmed`，只要工具修剪生效即标记 `context_changed = true` 并授权溢出重试，避免了不必要的 LLM 摘要调用。

### 终态越界检查点（Terminal Turn Checkpoint）

以前的压缩往往只在“发起下一次模型请求前”被动触发。如果 Agent 的某一次回复（收到 `EndTurn`）刚好使得上下文越过了阈值，若不及时处理，会话挂起后存储的快照就是超限的。

我们完善了终态判定：当检测到终态交互且 token 越界时，在 `MessageComplete` 之后、`TurnEnd` 之前立即执行压缩并持久化检查点。这确保了用户下一次唤醒会话时，拿到的永远是干净、紧凑的上下文。

## 4. 协同防御：分级循环守卫（Graded Loop Guard）

上下文急剧膨胀的一个常见诱因，是模型陷入工具调用的死循环（比如用相同的参数连续调用 3 次 `grep` 或 `read_file`）。

为了从源头减少无效上下文堆积，我们同步引入了分级循环守卫：
- **工具分类**：区分只读幂等工具与具有副作用的变更工具；
- **三级阶梯处置**：
  1. **Warn（警告注入）**：首次重复时在工具返回值中追加引导提示，提醒模型更换思路；
  2. **Block（合成拦截）**：二次重复时直接拦截底层工具执行，合成错误返回，既阻止无意义开销，又维持 `tool_use`/`tool_result` 协议配对；
  3. **Halt（安全终止）**：多次无效重试后触发熔断，向前端精确透传 `repeated_tool_calls` 状态，替换以往模糊的“达到最大轮次”文案。

## 5. 实测效果：40% Token 降幅与 99%+ Cache 命中率

在连续 47 小时、累计 1000 次请求（吞吐 4.90 亿 input tokens）的高强度长会话实测中，整套优化机制展现了显著的治理效果：

| 核心指标 | 优化前 (964 轮) | 优化后 (36 轮) | 变化趋势 |
| :--- | :--- | :--- | :--- |
| **均 Input / 轮** | 496,806 tokens | 299,625 tokens | **↓ 40%** |
| **上下文形态** | 175 万全量重放 (失控) | ~25 万起步 / 280K 平衡 | **健康受控** |
| **Prompt Cache 命中率** | 99.11% | 96.91% (含首请求重建) | **持续稳定 (后续 99%+)** |

### 核心收益与数据分析

1. **单轮输入 Token 骤降 40%**：
   - 优化前平均每轮 input 达到 **49.7 万**（496,806 tokens）；
   - 优化后平均每轮 input 降至 **29.9 万**（299,625 tokens），单轮 token 消耗大幅降低 **40%**。
2. **上下文形态健康可控**：
   - 优化前由于未及时剪枝和压缩，会话上下文一度膨胀至 **175 万** 全量重放；
   - 优化后引入增量压缩与检查点，会话在 **25 万** 左右平滑起步，并在 280K 上下维持动态健康增长。
3. **99%+ 极致 Prompt Caching 命中率**：
   - 全程 4.9 亿 input tokens 中，累计 Cache 命中率达到 **99.06%**。
   - 在优化后的 36 轮采样中，有 **33 轮请求的 Cache 命中率维持在 99%~100%**；仅在极少数由于压缩/中断而重建上下文的首请求出现短暂的重构 miss（约 2~2.3 万 tokens，命中率依然有 92%~95%），后续连续交互立即秒回 99%+ 顶峰。

## 总结

优化后的上下文管理架构，把原本不可控、易卡顿、易丢失信息的单点压缩，拆解为了一个**具备前瞻性（Prefire）、可追溯（Recovery Hint）、低成本（Prune-first）与防御性（Loop Guard）**的完整管道。

实测数据证明，让 Agent 跑得长、跑得稳，核心不仅在于模型本身的推理能力，更在于运行时 Harness 是否能把上下文流转治理得足够平滑与确定。
